---
title: Output handling
description: Receive PDF bytes in memory, as a stream, written to disk, or stored server-side.
---

The SDK gives you four ways to handle a rendered PDF: in-memory bytes, an `InputStream`, a write-to-disk helper, or a stored document on the server. Pick the one that matches how your code consumes the output.

## In-memory (`render().pdf`)

```java
byte[] pdf = client.render().pdf(input);
// pdf: byte[] — write, upload, return as-is.
```

Best for documents that fit comfortably in process memory.

## Streaming (`render().pdfStream`)

For large PDFs or piping straight to an HTTP response or object store, use `pdfStream` and let the SDK keep memory bounded. The returned `InputStream` owns the underlying HTTP connection — wrap it in `try-with-resources` or leak a connection slot. `requestTimeout` is an idle timeout here: it bounds the wait for the download's headers, then each `read()` that waits for the next bytes. The time you spend between two reads does not count, so a large PDF read at your pace is not cut off, but a storage connection that stops sending fails `read()` with `DOWNLOAD_FAILED` (`Failed to download PDF: timeout`). A connection that drops mid-body throws `DOWNLOAD_FAILED` (`Failed to download PDF: network error`) from `read()`.

```java
try (InputStream stream = client.render().pdfStream(input)) {
    Files.copy(stream, Path.of("./invoice.pdf"));
}
```

## Write to file (`renderToFile`)

`PoliPageClient.renderToFile(input, path)` streams bytes to disk with bounded memory. The PDF goes to a temporary file next to the destination, which is then moved onto it (atomically where the file system can): a call that fails or is cancelled never leaves a partial file. The destination is either as it was or replaced by the complete PDF (a cancel that lands once the download is complete may still replace it). A symbolic link is followed: the file it points to is replaced and the link stays a link. An existing file keeps its POSIX permissions; its owner and any other hard link to it are not kept, since the file is replaced, not rewritten. Missing parent directories are created. Before any request, the call fails with `io_error`, leaving everything as it is, when the target exists and is not a regular file (a directory, a FIFO, a device or a socket: `Failed to write PDF: <path>: not a regular file`) or is not writable, or when its directory is not writable; so a file that cannot be written never costs a render. The check reads attributes only and never opens the target. A file that cannot be written throws `io_error` (`Failed to write PDF: <reason>`, the JDK exception as `getCause()`); the download's own failures, a stall past `requestTimeout` included, throw `DOWNLOAD_FAILED`.

```java
client.renderToFile(input, Path.of("./invoices/INV-001.pdf"));
```

For async callers there's `renderToFileAsync(input, path)` returning a `CompletableFuture<Void>`.

## Server-side storage (`render().document`)

When you want the PDF to live on Poli Page's servers (for later download, preview, or thumbnails), use `render().document`. It returns a `DocumentDescriptor` carrying `documentId`, `presignedPdfUrl`, and metadata.

```java
DocumentDescriptor doc = client.render().document(input);
URL url = URI.create(doc.presignedPdfUrl()).toURL();
```

`presignedPdfUrl` has a 15-minute TTL. If it expires, call `client.documents().get(documentId)` to refresh.

## Example

```java
import java.nio.file.Path;
import java.util.Map;
import page.poli.sdk.PoliPageClient;
import page.poli.sdk.input.RenderInput;

class Example {
    public static void main(String[] args) {
        PoliPageClient client = PoliPageClient.builder()
            .apiKey(System.getenv("POLI_PAGE_API_KEY"))
            .build();

        RenderInput input = RenderInput.builder()
            .project("billing")
            .template("invoice")
            .data(Map.of("invoiceNumber", "INV-001", "total", 1280))
            .build();

        client.renderToFile(input, Path.of("./invoices/INV-001.pdf"));
    }
}
```
